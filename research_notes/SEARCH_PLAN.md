# Plan: policy + short search (what Stockfish #1 and calc #4 do)

Owner: Claude (plan, review, integration). Helpers: Codex (C++), opencode/LongCat (Python validation, data),
Kaggle/Colab (training, panels). Every stage has an audit gate before the next starts.

## Why
- Top teams: a small conv policy (Stockfish: 23 channels x 7x7 + 54 scalars -> conv32 -> conv32 -> dense128 -> 4 logits;
  ours: 16 planes + 3 scalars -> conv32 -> dense64 -> 6) + a short search per move: candidates = the policy's likely
  moves, each played out a few rounds with every dragon moved by the policy, scored by length difference (calc: 3 rounds,
  5 in the opening, UCB1 over spare CPU). Our rules choose with a 1-ply evaluation and static enemies: the head-on war and
  r40-150 economy losses (2-5x fewer pearls on mazes) are exactly where look-ahead pays.
- User constraint: rules stay the backbone; the network is a crutch; the endgame/queen rules (QFEED, QHIDE, SELFTRACK, ...)
  remain in charge where the network is blind.

## Stages
S0 Instrumentation (Claude, now): CPU budget per turn (points) of Y.9.1 by phase and length; how much headroom exists for
   rollouts (CPU limit 100M points/turn; we use ~5M rules + ~18M network).
S1 Local simulator (Codex, C++ in cand_r): `struct SimWorld` built from what the dragon sees + remembers (bodies, pearls,
   kelp/portals from KM, pearl countdowns); `step(world, actions)` applying the official order (ascending id, free sprint
   ceil(L/4), paid steps shed tail, collisions: head-on kills both, body/wall/self kills mover, eating, pearl drops on
   death (every 2nd segment), spawns from countdowns). Unknown cells = open water (calc); unseen dragons don't exist.
   Gate: opencode validation (S2) passes on >= 99% of steps.
S2 Validation harness (opencode, Python): from our replays, reconstruct each dragon's 7x7 world at a turn, run the C++
   step (via a tiny CLI built from the same header, or a Python port generated by Codex) and compare with the replay's
   next state inside the window. Report mismatch classes.
S3 Search (Codex, C++): for the acting dragon: candidates = top-3 options of the current chooser (rules+network order,
   safety class respected) + any option the network gives >= 15%; rollout depth 3 (5 for r<60); all visible dragons act
   by a cheap policy (network argmax if CPU allows, else the rules' greedy step) ; score = (our total length - theirs) in
   view + queen terms (our true queen alive / enemy queen dead weigh 50) + rules' safety; UCB1 extra randomized playouts
   with leftover CPU; keep the default move on ties. Hard CPU guard per turn.
   Gate: sandbox 80-game paired panel vs Y.9.1 (Kaggle) AND a 40-game panel vs vb21/vb19, plus per-game review of 5
   flipped games (analysis first, score second).
S4 Policy improvement (Kaggle/Colab): (a) richer inputs like Stockfish (23 channels: remembered map, pearl countdowns,
   queen flags, sprint reach) retrained on new-rules top-team games (ladder/slope_nr, 2000+ games by now);
   (b) optional later: distill search-improved move probabilities into the policy (Stockfish is trying it; calc found
   copying the search did not help) - only after S3 shows gains.
S5 Larper's loop (every cycle): for positions where a top team's move differs from ours, record "what our bot did" vs
   "what they did" and why theirs is better (opencode tooling: tools/move_diff.py on top-team replays: run our bot's
   evaluator on their states), then tune rules to reproduce the better move.

## Audit
Codex audits this plan before S1 starts (risks: CPU, wrong engine order, memory 48 MB, unknown-world bias). Claude audits
every Codex patch; opencode's validation audits the simulator.

## Audit outcome (Codex, ladder/cosci/audit_search_plan.md) -> plan amended (Claude, 2 Oct 06:20 IST)
- APPROVED first step = Codex's minimal S1/S3 ("SEARCH1"): simulateFrom(body,len,dirs) + deterministic 2-ply own-dragon
  search over the top 2 safe root options, one greedy continuation each, leaf = evaluate(); only when a visible enemy is
  within 6 or room < 2L+8; other bodies fixed, no pearl respawns; expansion-count cap + time backstop; never promote a
  lower safety class; keep the current move on ties. Gate: 80 paired games (Kaggle) + review of flipped games.
- Unknown cells stay UNKNOWN in any future SimWorld (not open water); portals modelled with uncertainty; fixed arrays /
  reversible deltas (48 MB); count evaluations, not just ms.
- Full SimWorld::step + opponent replies only after S2 replay validation shows exactness on covered events.

## Model size (dev advice, 2 Oct): keep the net small (~125-200k params, like Stockfish's conv32-conv32-dense128); data
quality and inputs (remembered map, pearl countdowns, queen flags, sprint reach) >> size; in-game CPU (100M points/turn)
is the rollout budget, so make the net CHEAPER (calc: 8x faster with identical moves); cloud = evaluation games + data.

## From "Learning to play Loong" (over-yonder.tech; large-scale RL writeup, 2 Oct): what we adopt, cheapest first
1. Symmetry: egocentric input (forward = up) + RANDOM LEFT-RIGHT MIRROR augmentation in training (mirror the crop and swap
   left/right labels). Check our ml/build_dataset.py + train.py + the C++ plane builder for both (Codex audit).
2. Inputs beyond 7x7: their 15x15 egocentric crop from REMEMBERED map + coarse whole-map overview + scalars (+ sonar set).
   Ours: 16 planes on 7x7 + 3 scalars. Add remembered kelp/portals/pearls/countdowns + queen flags + sprint reach.
3. Train on GENERATED maps (they held official maps out entirely) -> generalises to the new maps coming today;
   our maps_gen2/ (300 maps, new-engine format) + self-play data with the rules bot as teacher.
4. Hierarchical action head: move | sprint(2-8, each step conditioned) | split(size). Ours predicts only the first step.
5. CPU: int8 quantized weights + 16-bit activations (quantization-aware training) -> more budget for rollouts.
6. Engine copy verified on 100k games (126M dragon-turns identical): matches our S1/S2 gate.
7. Not feasible now: 44M-weight teacher + PPO league on 4xH100; on-policy distillation; GRU memory (later, if inputs plateau).
